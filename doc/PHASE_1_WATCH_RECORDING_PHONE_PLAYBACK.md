# Phase 1：手表录音 → 手机接收 → 手机试听

> 文档状态：`superseded` — 2026-08-28 的真机闭环证据仍有效，但批次上限、队列和索引能力已经演进；当前行为以 `doc/CURRENT_ARCHITECTURE.md` 为准。

## 目标

使用华为官方 Wear Engine 验证最小双端闭环：

1. 手表端申请麦克风权限并生成已封口的 PCM/WAV 录音。
2. 手表通过 Wear Engine P2P 把录音文件发送给已配对手机。
3. 手机接收录音并保存在应用沙箱。
4. 手机在应用内试听最近收到的录音。
5. 手机可点击“同步手表文件”，主动拉取手表当前应用沙箱内已封口的 WAV/M4A，并展示原文件名、大小和手表相对路径。
6. 连续 PCM 录音时，每个 1 分钟 WAV 原子封口后自动加入独立的串行发送队列；手机无需点击同步按钮即可接收新分片。

工程继续使用同一个 `entry` HAP，并通过设备类型展示不同页面：`wearable` 显示录音发送页，`phone` 显示接收试听页。最低兼容版本为 HarmonyOS API 23。

## 为什么使用 Wear Engine

- 使用华为运动健康中既有的手机与手表绑定、连接关系，不要求用户填写 IP。
- 文件传输和对端应用识别由官方能力完成，应用不维护 TCP 端口或自行选择蓝牙/Wi-Fi 链路。
- API 23 使用 `getConnectedDevices`、`transferFile` 和 `registerFileReceiver` 等 API 12 起可用的基础接口。
- 不使用 API 24 才提供的 `registerFileReceiverWithProgress` 和增强版远端启动接口。

## 开发者控制台前置条件

应用需要在华为开发者联盟申请接入 Wear Engine 服务，并为当前应用开通设备基础信息和 P2P 通信能力。`AppInfo.fingerprint` 在 HarmonyOS 应填写对端应用的 `appIdentifier`；本工程从当前安装包的签名信息动态读取。未申请服务时，真机接口会返回错误码 `1008500004`。

还必须从 AppGallery Connect 的“项目设置 > 常规 > 应用”取得 OAuth 2.0 `Client ID`，并在 `entry/src/main/module.json5` 的 `module.metadata` 中配置 `client_id`。Client ID 与 APP ID/appIdentifier 不是同一字段，不能互相替代。当前工程已配置 Client ID；是否已开通 Wear Engine 服务及相关能力，仍以真机返回结果为准。

## 使用步骤

### 手表主动发送

1. 分别把同一个已签名 HAP 安装到 API 23 手表和手机。
2. 在华为运动健康中确认手表已配对并处于在线状态。
3. 打开手机应用并保持接收页面运行。
4. 在手表点击“开始录音”，录制几秒后点击“停止录音”。
5. 点击“发送到手机”。
6. 手机出现“录音接收完成，可以试听”后，点击“试听录音”。

### 手机主动同步

1. 打开手机应用并等待页面显示已连接手表。
2. 点击“同步手表文件”。手机使用 API 23 基础版 `startRemoteApp` 尝试拉起手表，再通过 `sendMessage` 发送带 `requestId` 的同步请求。
3. 手表只枚举当前应用沙箱内已经封口的 `.wav`/`.m4a`；忽略 `.part` 和 JSON，逐个只读发送元数据与文件。
4. 手机把本次文件保存在 `files/synced_from_watch/<requestId>/`，列表展示原文件名、大小和手表相对路径。
5. 点击列表项可选择文件，再点击“试听选中文件”。

### 分片自动同步

1. 先打开手机接收页并保持前台，再在手表开始“PCM 无缝分段测试”；手机无需点击“同步手表文件”。
2. 手表在写回 WAV 头、`fsync`、关闭文件并把 `.part` 原子改名为 `.wav` 后，才把该封口文件加入自动发送队列。
3. 录音回调不等待网络；发送队列在旁路串行处理，避免 Wear Engine 传输阻塞持续采集和下一分片封口。
4. 手机收到 `auto_file` 元数据与文件后，将其保存到 `files/synced_from_watch/auto_<批次>/`，并立即在列表展示原文件名、大小及手表相对路径。
5. 对端未打开、离线或传输失败时，分片保留在手表且不会删除、覆盖或移动；待传队列写入 `automatic_sync_queue_v1.json`，进程重启后恢复仍存在且大小匹配的条目，遗漏文件仍可由手机按钮补拉。
6. 手机手动同步若遇到正在发送的自动分片，不再返回“另一项同步”错误；本次请求会排队，并在当前文件结束后优先执行，手机页面保持同步中并显示排队原因。
7. 文件或元数据发送遇到 Wear Engine 短暂通信失败时，手表最多重试 3 次并重新获取对端通道；持续失败则结束当前批次并保留源文件和自动待传队列，不再把后续几十个文件逐个快速标成失败。

## Phase 1 边界

- 单个录音最大 10 MB。
- 当前一次手动同步请求最多发送 1 个缺失文件；库存键每页 24 个交换，页面可继续点击补拉剩余文件。
- 手机接收页面需要保持打开，暂不实现后台接收和断点续传。
- 当前按钮执行全量同步；重复点击会建立新的 `requestId` 批次，不会删除或覆盖手表源文件。
- 自动同步只处理本次连续录音中新封口的分片；它不扫描或自动上传历史文件，历史与进程重启后的遗漏仍由手机按钮补拉。
- 自动发送与手机全量同步共用串行传输闸门，避免两个文件流交错；手机全量同步到达时会等待当前自动文件完成，随后优先执行，无需用户重复点击。
- 手机使用 `synced_from_watch/received_index_v1.json` 持久化历史索引；索引缺失或损坏时会扫描同步目录和旧 `received_*.wav` 重建列表。
- API 23 接收端没有文件传输进度回调，文件完整到达后才更新页面。
- 收到的文件保存在手机应用沙箱，卸载应用会删除这些文件。
- 构建通过只代表静态和打包验证；最终验收必须在 API 23 手表和手机上完成一次真实录音、官方传输和播放。

## 2026-08-28 真机结果

- 手表主动发送稳定性：修正 API 23 `transferFile` 的进度回调与空成功结果后，最终版本连续发送 3 次，手机端大小和 SHA-256 全部一致，手机显示“播放完成”。
- 手机主动同步：手机清单显示 18 个已封口 WAV，最终收到 `18/18`、跳过 `0`。
- 手机同步目录：18 个文件，共 `2619672` 字节；与手表对应的 18 个音频逐项 SHA-256 比对，差异数为 `0`。
- 手表保护性复核：安装前后及同步后均为 21 个文件、`2623981` 字节；同步前后目录递归比较无差异。
- 手机页面成功展示文件名、大小和手表相对路径；选择同步文件后试听显示“播放完成”。
- API 23 的 `startRemoteApp` 在对端已运行时可能返回 `203`；实现将拉起动作视为尽力而为，以随后 `sendMessage` 的结果作为同步通道是否可用的权威判断。

### 自动同步待验收项

- 连续录制至少 3 个完整 1 分钟分片，全程不点击手机“同步手表文件”，确认手机逐片自动出现。
- 对每个自动收到的文件逐项比较手表源文件与手机副本的大小及 SHA-256，并在手机完成试听。
- 复核安装前既有手表文件未被删除、移动或覆盖；本轮只允许新增测试会话和手机副本。

## 验收标准

- 手表首次录音时能正常请求麦克风权限。
- 录制超过 1 分钟后能生成非空、已封口的完整 WAV；提前停止时最后一个不足 1 分钟的分片也能正常封口。
- 手机与手表无需输入 IP，即可通过 Wear Engine 互相识别。
- 手机能完整收到录音，显示文件大小，并可试听刚刚录制的声音。
- 未开通服务、设备离线、对端未安装或未运行时，界面给出可理解的失败提示，应用不崩溃。
- 连续 3 轮传输后，手机文件与对应手表源文件的大小及 SHA-256 均一致，且手表源文件仍保留。
