# Phase 1D：Watch 5 睡眠模式联动探针

## 目标

验证 Watch 5 用户开启或关闭“睡眠模式”时，第三方 wearable 应用能否收到可用于自动暂停、恢复录音的公开系统事件。本阶段只记录事件，不自动控制麦克风，也不改变 Phase 1C 的 PCM 分段实现。

## 监听范围

- 进入、退出强制休眠。
- 进入、退出休眠。
- 设备空闲状态变化。
- 省电模式变化。
- 屏幕开启、关闭。

每次应用页面创建时自动启动动态订阅，并将事件同步写入应用沙箱：

```text
files/sleep_mode_probe_<启动时间>.jsonl
```

页面底部显示探针状态、最近事件和累计事件数。

## 真机测试步骤

1. 覆盖安装测试 HAP，保留既有录音沙箱。
2. 打开应用，确认页面底部显示“联动探针已启动”。
3. 点击“开始 PCM 测试”，让录音长时任务保持进程活动。
4. 正常熄屏约 10 秒后重新亮屏，作为屏幕事件基线。
5. 开启 Watch 5 睡眠模式，等待约 10 秒。
6. 关闭 Watch 5 睡眠模式，再等待约 10 秒。
7. 停止 PCM 测试。
8. 导出最新 `sleep_mode_probe_*.jsonl`，检查睡眠模式切换前后的事件序列。

## 判定

- 若睡眠模式开关稳定触发区别于普通熄屏的公开事件，可将该事件接入录音状态机。
- 若只出现 `SCREEN_OFF/SCREEN_ON`，或完全没有睡眠模式专属事件，则不能把公开公共事件当作可靠联动信号，应改用应用内睡眠时间表、手机侧协调或获批的运动健康睡眠状态能力。

## 第一轮真机结果（2026-08-24）

测试 HAP 已覆盖安装到 Watch 5，原有应用沙箱和录音文件均保留。用户开启、关闭睡眠模式并返回应用后，页面表现为重新打开；系统日志证实这不是单纯的 UI 重绘，而是创建了新的应用进程与 `UIAbility` 实例。

### 公共事件

探针实际收到：

```text
usual.event.SCREEN_OFF
usual.event.DEVICE_IDLE_MODE_CHANGED
usual.event.SCREEN_ON
usual.event.SCREEN_ON
usual.event.DEVICE_IDLE_MODE_CHANGED
```

未收到：

```text
usual.event.ENTER_FORCE_SLEEP
usual.event.EXIT_FORCE_SLEEP
usual.event.ENTER_HIBERNATE
usual.event.EXIT_HIBERNATE
usual.event.POWER_SAVE_MODE_CHANGED
```

因此，Watch 5 的用户“睡眠模式”没有映射为本探针可接收的公开睡眠/休眠公共事件。`SCREEN_OFF/SCREEN_ON` 也不能作为替代信号，因为普通熄屏、抬腕亮屏同样会触发。

### 进程与录音证据

- 原进程 PID 54615 在 23:02:40 进入后台，返回应用时于 23:03:25 创建新进程 PID 55750，并重新执行 `Ability onCreate`。
- PID 55750 在 23:03:34 进入后台，返回应用时于 23:04:11 再次创建新进程 PID 55830，并重新执行 `Ability onCreate`。
- 两个录音会话都没有生成 `session_summary.json`，而是留下 `.wav.part`，说明没有走到应用的正常停止与 WAV 封口路径：
  - `pcm_gap_test_1787583756353`：约 8.90 秒采样后中断。
  - `pcm_gap_test_1787583809780`：约 9.14 秒采样后中断。
- 两次旧探针日志都只有 `probe_started`，没有 `probe_stopped`，与进程被非正常终止或回收一致。

目前日志缓冲区中没有保留明确的系统 `kill_reason`，因此不能仅凭本轮证据断言具体终止策略名称；但“进程发生重建”和“录音未正常封口”已经由 PID、Ability 生命周期及沙箱文件三类证据交叉确认。

## 结论

当前公开 wearable API 不能可靠地直接订阅 Watch 5 用户睡眠模式开关，因此暂不把公共事件接入自动停录/恢复。下一步可选路线：

1. 应用内维护睡眠时间表，在系统睡眠模式预计开启前主动封口停录。
2. 手机侧协调睡眠/免打扰状态，再向手表发送明确的暂停、恢复命令。
3. 申请运动健康行业能力，订阅实际睡眠状态；该信号是睡眠识别结果，可能晚于用户开启睡眠模式。
4. 增加 `.wav.part` 启动恢复，避免进程异常终止后丢失最后一段已经写入的 PCM。

## 后续处理状态（2026-08-24）

第 4 项已由 Phase 1E 完成：应用启动时扫描旧会话，有 PCM 的 `.wav.part` 会补写正确 WAV 头并原子改名，44 字节空备用槽会清理，同时写入 `recovery_summary.json`。实现已通过 API 23 工程构建和 Watch 5 真机验收。

安装恢复版本前，4 个 `.wav.part` 原件已复制到电脑，尺寸和 SHA-256 与手表端逐一一致。两次中断会话分别恢复出 3.900 秒和 4.140 秒 WAV，恢复前后的 PCM 区域逐字节一致；两个 44 字节空槽已清理，失败列表均为空。应用再次冷启动后 WAV 与报告哈希不变，沙箱中没有残留 `.wav.part`。
