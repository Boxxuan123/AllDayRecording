# 录音完成协议

录音有三个独立状态：

1. **分片已上传**：电脑完成单个 WAV 的哈希校验，手机立即持久保存该文件的 SHA-256 回执。
2. **整场已备份**：手机收到手表停录时写出的 `session_summary.json`，核对片数、总样本数和每片位置；电脑核对全部 WAV、连续性、总样本数后返回 V3 会话入库回执。手机保存清单哈希作为会话回执。
3. **当前输入已转写**：电脑按完整清单对应的输入版本完成处理。旧输入版本的成功任务不能代替这个状态。

手表仍然逐片同步 WAV。停录后，`PcmSegmentedRecordingService` 写出原始结束记录，并将其排入同一个持久自动同步队列。手动同步扫描也包含这份记录。手机可以在结束记录到达前上传已收到的 WAV，但此时不会提交电脑会话清单。

电脑会话清单使用 `AllDayRecording session manifest v2`，并包含 `completion`：`source`、`completedSegments`、`totalSamples`、`confirmedAt`。手机只在原始手表结束记录与全部 WAV 一一对应时使用 `watch_stop`。旧协议没有结束记录时，用户必须在手机上查看当前片数和样本数，确认手表已停录且分片已全部同步；该确认以 `legacy_user_confirmed` 保存。若确认后又收到分片，旧确认不再匹配，必须重新核对；已取得电脑整场回执的会话需要走修复流程。

电脑拒绝新的 V1 清单、缺少结束证明的 V2 清单、证明与清单不符、分片缺失或不连续的清单。已入库的 V1 清单允许相同哈希的幂等重放。手机只有在响应中看到 `automation.v3` 的会话 ID、清单哈希和入库状态后才显示“整场已备份”；单个文件的 `completed` 响应仅显示“分片已到电脑”。

后续检查是否需要重传时，手机将已保存的会话回执 SHA-256 与当前完整清单的 SHA-256 比对；片数和总样本数相同也不能复用不同清单的回执。对已有逐片回执的 WAV，提交清单时跳过音频重哈希与逐片网络查询。如果电脑报告清单引用的录音缺失，手机并发重新核验、补传，再重试清单提交。

## 清单追加与失败恢复

电脑保留原始 `session_manifests`，每次合法追加写入 `session_manifest_revisions`，返回递增的 `input_revision`。相同 SHA-256 重交返回原有确认；新版必须保留旧清单的会话身份、音频格式和全部旧分片元数据，旧分片 SHA-256 也要与已入库音频一致，只允许在末尾连续增加分片。违反规则的请求返回具体冲突原因，不会替换旧版本。

手机数据库独立保存每片 SHA-256、整场清单 SHA-256 与 `input_revision`，以及每条录音的失败类别、原因和下次重试时间。网络失败按时间重试；同一清单的冲突停止自动重试，清单改变后才重新进入自动处理。手动上传页显示失败原因，提供单条录音重试入口；一条录音失败时继续处理其他录音。整场回执写入与清除旧失败状态在同一数据库事务内完成。
